# ZSMTP Protocol

**Zcash Simple Money Transfer Protocol.** A federated, SMTP-like protocol for
privately sending Zcash between users, run between daemons. This is the design
in progress.

## Transport

ZSMTP runs over two transports:

- **`zsmtp.sock`** (Unix socket) — local daemon-to-daemon receive.
- **TCP with implicit TLS** (`zsmtp_listen`, default `0.0.0.0:465`) — network
  exposure, SMTPS-style (TLS from the first byte, no STARTTLS). Shares the
  `[tls]` cert/key with IMAPS. The ZSMTP domain-key handshake runs on top of
  TLS: TLS authenticates the *channel*, domain keys authenticate the *servers*.

## Command set (implemented)

Line-based commands with CRLF framing and length-prefixed binary blobs
(`BLOB <n>\r\n<bytes>` — no SMTP dot-stuffing):

| Command | Direction | Purpose |
|---|---|---|
| `HELLO <domain>` | client → server | Greet (SMTP `EHLO` analog) |
| `AUTH <challenge-b64>` | client → server | Server auth: client issues a signed challenge; server signs it back |
| `ADDR <ephemeral\|attested> <user>` | client → server | Request an address + pubkey attestation |
| `INVOICE <sender-user> <msg-id> <sealed\|plaintext>` + blob | client → server | Deliver a sealed invoice |
| `STATUS <code> <message>` | server → client | Reply |
| `QUIT` | client → server | End session |

Status codes mirror SMTP classes: `2xx` success, `3xx` continue, `4xx`
transient (retry later), `5xx` permanent. `250 accepted into inbox` is
"accepted by next hop", not "received by user". No end-to-end ack.

## Why federated (not ENS-like)

ENS-style central registries work for transparent systems, where an address is
a stable identity and unlinkability is not a concern. They are fundamentally
unsuited to shielded addresses, where:

- **Address rotation is practically a given** — fresh addresses per payment to
  preserve unlinkability.
- **Anonymity/unlinkability matter most** — a registry binds an identity to an
  address, which is the opposite of the point.

A federated model, like email, keeps discovery distributed. Contacting a light
indexer reveals your IP and *that you requested a specific identity* — with no
PIR, the indexer can log every request. We do not claim to solve that entirely;
the design intent is to shrink the attack surface from "a general indexer which
logs every request" to **only the intended server** (the one the sender already
knows about via DNS).

## Protocol overview

Servers expose a service on a standard port or via an SRV record. The exchange
is a CEI (Commit-Effect-Interact)-style protocol for revealing addresses.

### 1. Server authentication (domain keys)

Both servers authenticate as true to their DNS via **domain keys** (DKIM-
style).

1. The sending server sends a random scalar challenge, signed with its own
   domain key (`HELLO` + `AUTH`).
2. The receiver signs the challenge with its domain private key and returns it.
3. Server authentication succeeds — the receiver has proven control of its
   domain key. The challenge binds both parties' domains, a session nonce, and
   a timestamp (replay + staleness protection).

Open (see [`decisions.md`](decisions.md)): whether authentication is mutual
(the receiver challenges the sender back).

### 2. No user authentication at the ZSMTP layer

There is **no user authentication** at the ZSMTP layer — users authenticate
locally against `secure_mailbox.sock`, not over the wire.

Note: a deniable ECDH session (commit-and-reveal) is documented as future work;
the current transport security is TLS (TCP) / Unix socket (local).

### 3. Address + pubkey attestation request

The sender requests an attestation of an **address and an encryption pubkey**
for a queried user (`ADDR`). The server attests to **both** under one
domain-key signature, so the pubkey the sender encrypts to is bound to the
address it was told to pay — preventing pubkey substitution. Unknown users are
rejected with `550 no such user`. See [`attestation.md`](attestation.md).

Two issuance modes, requested explicitly:

- `ephemeral` — a fresh, one-shot address generated on demand per request.
- `attested` — a stable address + pubkey signed by the server / a recognised
  identity instrument.

### 4. Sealed invoice

- The **invoice is generated by the sender** (`INVOICE <sender-user> ...`).
- The sender's username rides in the envelope; the sender mailbox
  (`user@domain`) is built from it plus the authenticated peer domain.
- The invoice is **sealed** before delivery:
  - **Shielded recipient:** encrypted with key `K`; `K` is sent as the on-chain
    shielded memo.
  - **Transparent recipient:** encrypted to the recipient's attested public
    key. Only a hash `H(invoice)` is committed on-chain via `OP_RETURN`.
  - In both modes the invoice content is private and the server is blind.

### 5. Acknowledgment and address confirmation

The server acknowledges receipt of the (sealed) invoice with `250 accepted into
inbox` (or `550`/`450` on permanent/transient failure).

### 6. Payment

The sender sends the ZEC, attaching the binding (`K` in the shielded memo, or
`H(invoice)` via `OP_RETURN`). The sender then notifies the recipient; **this
notification is entirely optional**.

## IVK handling (D10 resolved)

**The server never holds the IVK.** Decryption is the client's job — the
receiving server is a dumb ciphertext store. The only exception is the
optional, per-user IVK registration that enables dynamic addresses, and even
then the IVK lives inside a swappable `AddressProvider` boundary, not the main
daemon (see [`attestation.md`](attestation.md)).

The IVK owner fetches the sealed invoice from the mailbox (IMAP) and decrypts
locally against their own transaction history. Because the invoice is sealed
with a key only the recipient can recover, the server **does not learn the
invoice contents** even though it stores the blob. This works without the user
being online.

## The binding (deniability + self-consistent record)

The on-chain artifact — `K` in the shielded memo, or `H(invoice)` in
`OP_RETURN` — is the keystone. Everything in the ZSMTP transcript is opaque
without the recipient's key material, and the binding only decrypts / verifies
under the recipient's control.

Two purposes:

1. **Deniability.** An interceptor with every key *except* the recipient's key
   material sees two servers exchanging encrypted blobs, but cannot decrypt the
   invoice, cannot link any on-chain tx to it, and cannot prove the blobs were a
   payment attempt at all.
2. **Self-consistent record.** The recipient recovers the binding, unlocks the
   stored invoice, and obtains the record: *on-chain tx ↔ invoice*.

### Inbox state machine

The recipient's server must store the sender-delivered invoice blob *pending*
the binding. It is useless alone (deniable) and becomes meaningful only when the
chain scan produces it. Per-inbox-entry states:

1. `opaque` — awaiting the on-chain binding.
2. `resolved` — invoice unlocked by the binding.
3. `spent` — the underlying note is spent.

## Privacy model

Three axes:

- **Who is paying** → hidden (shielded by default).
- **What is being paid** → hidden (shielded by default).
- **Who is being paid** → hidden *unless the recipient opts in* via an attested
  address (exchanges, public identities).

The attestation is an **opt-in deanonymization**, not a protocol requirement.
Private recipients use `ephemeral` addresses; exchanges use `attested` addresses
because their deposit address is public anyway.

## Claims and caveats (tightened)

- **Proof-of-integrity is delivery, not receipt.** The server signing a *sealed*
  blob proves "an invoice blob was delivered via this server," not that the
  recipient read its contents. **Offline recipient XOR non-repudiable receipt.**
  The honest claim: the sender's delivery is non-repudiable; the recipient's
  awareness is not proven.
- **Transport vs content.** On TCP, TLS (implicit, SMTPS-style) protects the
  *channel*; the domain-key handshake authenticates the *servers*; the invoice
  payload is sealed to the recipient. Content confidentiality comes from the
  application layer, not the transport.
- **Connection is observable.** The fact of connection (IP, timing, server
  logs) is observable by the server and network. Accepted scope reduction, not
  connection anonymity.
- **The server never holds the IVK.** Decryption is client-side; optional IVK
  registration is an explicit scanning delegation (inside the
  `AddressProvider`).
- **Transparent invoices are private.** Only `H(invoice)` appears on-chain via
  `OP_RETURN`; the content is sealed to the recipient's public key.
- **PIR is future work.** Because the sender already knows which server it is
  querying (via DNS), PIR does not apply to address lookup itself; it is an
  enhancement for other queries, not a stated goal.

## SMTP reference

Session mechanics to mirror:

- Line-based request/reply session with 3-digit status codes:
  `2xx` success, `3xx` continue, `4xx` transient fail (retry later),
  `5xx` permanent fail (give up).
- `Message-ID`: globally-unique id from the sender, used for dedup across relays.
- `Received:` chain: each relay appends a header, creating an audit trail.
- DKIM/SPF: sending domain signs the message; the receiving MX validates via DNS.
- Routing via DNS records — the record tells you where to deliver.
- "accepted by next hop" acknowledgments only, not "received by user".
- Queuing and retry with backoff on `4xx`; `5xx` is permanent.

### SMTP → ZSMTP mapping

| SMTP concept | ZSMTP translation |
|---|---|
| MX + DNS routing | DNS record / SRV → where to find recipient's daemon |
| `Message-ID` dedup | Mandatory unique message id |
| "accepted by next hop" | "Accepted into inbox" — not "received by user" |
| No end-to-end ack | Same — already decided |
| 4xx vs 5xx | Transient (resend later) vs permanent (outbox quarantine) |
| DKIM/SPF validation | DNS domain-key validation of the sending server |
| Session commands | State machine — greet, identify, deliver |

Things SMTP got wrong that we should not copy:

- No auth between servers → sending server should be cryptographically identified
  from the start (domain keys).
- Email trusts the relay → here the recipient daemon verifies against the
  chain/indexer, so forgery is impossible anyway.

## Open protocol questions

- Mutual server auth: does the receiver challenge the sender back (O10)?
- Deniability stance on the domain-key ack (is "the servers communicated"
  provable, or must it be hardened too?) (O8).
- Exact format of the sender-generated invoice, plaintext vs sealed fields.
- Which signature instrument / keyserver to standardize on (keybase.io was shut
  down in 2023; a live alternative or on-ledger anchoring must be chosen).
- Future "command mail": a standards-shaped SMTP facade where users email
  commands to the server (deferred, not part of the daemon-to-daemon path).
