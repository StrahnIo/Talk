# Decisions and Open Questions

## Decision log

### D1 — Non-custodial daemon
The daemon holds **viewing keys only**. It cannot spend on its own; the spending
key stays with the user/caller.

### D2 — Trusted lightwalletd indexer
The daemon uses a trusted lightwalletd indexer as its view of chain truth. It
knows all transactions and revealed nullifiers up to a given block height.

### D3 — No end-to-end acknowledgment
SMTP-style at-most-once delivery. Invalid inputs (forged / foreign / spent) are
silently dropped to an outbox. No bounce is generated.

### D4 — Authentication is the signature
The spend-auth signature over a transaction *is* the proof of identity. The
signing key is the account; no separate account system.

### D5 — Three sockets
`secure_mailbox.sock` (local, user-authenticated), `mailbox.sock` (HTTP/2-
exposed, disabled by default), `zsmtp.sock` (outbound delivery, sign-then-send).

### D6 — Invoice generated by sender; signature on the address
The keybase signature attests **address ownership** (identity↔address). The
invoice is **sender-generated** and does not touch the identity key.

### D7 — Memo key `K` as keystone
Invoice is encrypted with `K`; `K` is sent as the on-chain memo. Provides both
deniability (unprovable sending attempt without the receiver's IVK) and a
self-consistent record (on-chain tx ↔ invoice).

### D8 — Address issuance policy
`ephemeral` (fresh one-shot address, private recipients) vs `attested` (stable
deposit address + signature, exchanges).

## Open questions

### O1 — Indexer trust model
Whose full node / indexer, and what happens if it disagrees with the actual
chain? (Assumption: lightwalletd connected to a trusted node; exact failure
story TBD.)

### O2 — In-band delivery
Encrypted note (as on-chain) vs decrypted note data. Encrypted delivery is what
the chain does anyway and avoids leaking amount/memo to inbox message observers.

### O3 — Pending state
If the daemon's sync height is behind the block a delivered note claims, accept
as "pending" and confirm on next refresh (recommended) vs reject until the daemon
has seen that block.

### O4 — HTTP/2 shape for mailbox.sock
gRPC vs JSON REST; TLS vs h2c; auth model when reverse-proxied.

### O5 — Socket callers
Third-party wallets as socket callers? If supported, tx-signing-only auth is the
ceiling; no fine-grained per-operation control. Who is the socket caller — our
own client only, or arbitrary wallets?

### O6 — Sender identity model
SMTP's `MAIL FROM` is server identity; here the money is authorized by the
user's signature. Likely two envelope fields: sending server (DNS-verified) and
authorizing user (spend-auth signature).

### O7 — Getting the note plaintext to deliver
The sender's client constructed the shielded output, so it has the note data.
Needs confirming as part of the send path.

### O8 — Deniability stance on the domain-key ack
The ack is a verifiable, signed statement that a request occurred. It does not
reveal contents, but it does prove the servers exchanged a request. Either
accept "contact is provable" (deniability is about content/payment, not contact)
or harden it (ack computed but not persisted server-side, or encrypted under the
session key so a transcript leak proves nothing post-hoc).

### O9 — Signature instrument choice
keybase.io was shut down in 2023 (acquired by Zoom). A live "another keyserver"
must be chosen before this is buildable.

### O10 — Server auth details
Exact signed-challenge format for domain-key auth: whether the challenge binds
both parties' IDs, a session nonce, and a timestamp; whether the server's own
signature on the challenge is needed at all; whether auth is mutual.

### O11 — ECDH binding
Whether the ECDH session-key exchange is bound to the domain-key auth, and
whether commit-and-reveal alone is sufficient against MITM / signature-relay
attacks.

### O12 — Address/invoice ordering
Is the shielded address supplied up front, or only at the end after invoice
acknowledgment?

### O13 — Standalone challenge-response
Whether a standalone challenge-response for interactive login is wanted (raw
RedJubjub over a nonce, verified against `ak` derived from the FVK). Note: only
a custom client can produce it — no third-party Zcash wallet supports shielded
message signing today (ZIP 304 is a draft and undeployed; no Orchard or UA
equivalent exists).

## Next steps

1. Design ZSMTP protocol command set, envelope, status codes, message id, dedup,
   retry semantics.
2. Resolve O8 (ack deniability) — load-bearing for what the server persists.
3. Resolve the remaining protocol questions in [`zsmtp.md`](zsmtp.md).
4. Design secure_mailbox.sock (user-facing signing interface).
5. Design mailbox.sock (HTTP/2 exposure, reverse proxy).
